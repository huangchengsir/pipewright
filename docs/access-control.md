# 团队与权限

多租户模式由部署环境控制，不能在网页中临时切换。未开启过的实例不配置 `PIPEWRIGHT_MULTI_TENANT` 时，保留原单管理员体验。

## 开启与关闭

先备份数据库、数据目录和保险库主密钥。等待运行、部署、升级和待核对的外部操作收尾，停止旧进程，再设置环境变量并启动：

```sh
PIPEWRIGHT_MULTI_TENANT=true ./pipewright
```

systemd 部署在服务的环境配置中增加 `Environment=PIPEWRIGHT_MULTI_TENANT=true`，重新加载服务配置并重启。Docker 部署把 `PIPEWRIGHT_MULTI_TENANT=true` 传入容器环境并重新创建容器；仅修改宿主环境后执行容器 restart 不会更新容器环境。

Compose 可增加 `compose.access.yml`：

```yaml
services:
  pipewright:
    environment:
      PIPEWRIGHT_MULTI_TENANT: ${PIPEWRIGHT_MULTI_TENANT:?set true or false explicitly}
```

在 `.env` 明确配置 `PIPEWRIGHT_MULTI_TENANT=true`，然后使用原 Compose 文件及此覆盖文件重新创建服务。不要删除数据卷。关闭时保留该覆盖文件，把值改为 `false`，等待操作收尾后重新创建服务。

参数仅接受小写 `true` 或 `false`，不接受空值、`1` 或 `yes`。曾经开启过的实例必须持续明确配置该参数；遗漏配置会拒绝启动，避免意外降级。切换遇到未收尾操作时会拒绝切换，应恢复原模式，核对并完成原操作后再尝试。不要修改数据库中的模式标记绕过检查。

首次开启时，原管理员保留实例管理权限，旧资产归入默认团队。关闭时仅原管理员可以登录，团队、员工和权限数据保留；再次开启不会恢复已撤销的登录会话或 MCP 令牌。模式切换后需要重新登录，按新的权限重新创建 MCP 令牌。

## 员工、团队与角色

实例管理员创建员工并分配团队、角色和数据范围。新员工及重置密码后的员工使用临时密码，首次登录必须修改密码；管理员重置不会展示旧密码。员工在自己的账户页面修改个人资料和密码。禁用员工、移除成员或撤权后，旧会话和正在使用的功能也受当前权限检查约束。

每个团队初始化四个角色：团队管理员、维护者、发布者、只读成员。它们带有默认菜单和动作权限，但普通角色的成员必须明确分配资源范围；空范围不会自动变为全团队。发布相关的默认权限仅用于明确授权的测试环境，生产环境与服务器、凭据、Kubernetes 执行权限需要单独授权。团队管理员不等于实例管理员。

角色编辑器分别配置菜单、按钮动作和每个动作的数据范围。例如可以允许读取多个项目，但只允许发布项目 A 的测试环境。读权限不会自动授予下载、发布、终端或删除权限。多个角色不能把一个角色的动作与另一个角色的数据范围拼接成额外授权。

默认角色只在初始化时创建。重启、升级不会覆盖已编辑的角色或复活已删除的角色；新增权限不会自动赋给已有角色。

## 员工的第三方登录

实例管理员配置 GitHub、GitLab、Gitee、Google、Microsoft 登录应用。员工先登录自己的账户，再绑定自己的第三方身份；同一员工可以绑定多种平台。身份以提供商及稳定用户标识关联，不按相同邮箱自动合并账户，也不允许一个第三方身份绑定多个员工。

第三方登录不绕过员工禁用、强制改密、团队成员关系或数据权限。关闭多租户模式后，其他员工不能继续通过第三方登录进入实例。应用 Secret 只通过设置中的安全入口录入，不放入日志或共享配置。

## 执行与恢复边界

菜单隐藏和按钮禁用只是界面反馈。HTTP、MCP、后台任务、日志、制品以及执行目标仍由服务端授权。排队后的执行、长连接和后续采样会检查撤权及模式变化。

团队范围不等于操作系统沙箱。共享 SSH 主机、Docker 套接字和集群管理员凭据可能具备超出业务资源的能力；按团队隔离执行主机、命名空间和凭据，并只授予所需权限。本地执行能力仅供实例管理员使用。

数据库迁移必须同时保留员工、角色、成员范围、资源归属、禁用和撤销记录。使用平台的维护窗口迁移流程，不单独复制权限表，也不要更换保险库主密钥。真实第三方登录仍需使用各平台配置的应用完成验证。
